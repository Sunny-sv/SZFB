## 一、背景与要解决的问题（基于飞书调研）

**结论先行（建议理解，非已定）：** 分拨中心当前排班偏经验驱动，货量波动、请假旷工、到车不齐会放大「人等多 / 货等人 / 忙闲不均」。智能排班要解决的是：**在可预知货量与班次约束下，更稳地决定「谁上哪个班、哪类岗」**；是否进一步做到「谁卸/装哪辆车」属于进阶能力，**【待确认】**是否纳入首期。

基于飞书调研材料（智能排班系统调研、业务架构、基础数据），现场与管理侧反复出现的问题可归纳为：

1. **上班前：班次人数与岗位结构难对齐预测货量**  
   分拨货量按小时、环节、路由波动大；若提前一周只有粗粒度经验，容易出现正式工/外包配置不合理、班次偏好与出勤冲突、岗位技能匹配不足。

2. **班中：到车与货流变化后，补位慢、指派乱**  
   预计到达、卸车、移动（移库/移货）与实际偏差时，调度靠口头与即时判断；忙闲判断缺少统一口径，压车与等待交替出现。

3. **突发：请假、旷工、卡班、靠台变更缺少标准补位路径**  
   调研覆盖「突发如何处理」：目前多为人工临时拉人，补位时长与质量（差错、件均重匹配）难追踪。

4. **目标画像不清晰会拖垮系统边界**  
   调研目标写到「员工画像 → 微观指派到人/组、装卸哪辆车」。这与「只做班次人数」是两条产品路径，**【待确认】**首期停在哪一层，避免一上来做全量微观指派导致数据与对接过重。

5. **适用范围不能默认全开**  
   【待确认】先在哪些分拨试点、哪些环节（卸/装/移等）、是否区分正式工与外包编制规则。**禁止默认「全网分拨、全工种一次上线」。**

## 三、同行与行业对照（智能排班，不是装车排版）

**说明：** 此前做过的装车「排版」（车厢内货物摆放/码放）竞品调研与本题「人的智能排班」不是同一题，此处一笔带过，避免混用结论。

### 3.1 学术 / 行业：货量预测 → 班次人数优化

公开研究路径常见为：**先预测分时货量，再优化班次与用工结构（正式工 vs 临时工/外包）**，目标包括控制预测误差、平衡小时人效、降低加班与闲置。有 2025 年前后公开论文口径提到预测误差可到约 7% 量级、并显式区分正式工与临时工排班——可借鉴的是「预测误差带进排班约束」与「用工类型分规则」，**不是**把对方模型直接当我方方案。

**【待确认】** 我方是否首期就区分正式工 / 外包两套编制与成本约束。

### 3.2 专利向：装卸小组预约与调度

公开专利 CN110348613B 一类方案强调：**预约月台 + 调度装卸小组**。对分拨的启发是「车/台 ↔ 小组」的预约关系可以成为微观指派的骨架；但专利不能直接当产品需求，落地仍取决于我方月台、靠台、卡班与小组编制数据是否齐全。

### 3.3 京东公开能力分层：可借鉴「采纳方式」，不是照搬派车

京东公开的派车/调度能力常见分层表述为 **全自动 / 半自动 / 人机协同**。建议借到排班的是**结果采纳方式**：

- 算法给出班表或指派建议；
- 调度员确认后发布；
- 系统不在无人知晓的情况下改写已发布班表。

**【待确认】** 首期默认半自动（建议 + 确认）还是部分场景允许全自动发布。

## 四、建议产品定位（建议，非已定）

**建议一句话：** 智能排班是分拨中心的「人效与班次协同系统」——**对人**：建议谁上哪个班、哪类岗；**对车（进阶）**：建议谁卸/装哪辆车（微观指派）。

### 4.1 分层能力（建议架构，非已定上线顺序）

| 层级 | 含义 | 建议态度 |
| --- | --- | --- |
| L1 货量与人力预测 | 分拨 / 环节 / 路由 / 小时级预测，输出「需要多少人、哪类岗」 | MVP 建议必做（精度口径【待确认】） |
| L2 班次编制 | 生成可发布的班次人数与人员名单（含正式工/外包规则【待确认】） | MVP 建议核心 |
| L3 现场任务指派 | 到车后的卸/装/移微观指派到人/组 | 建议进阶；是否进 V1.1【待确认】 |
| L4 异常补位 | 请假、旷工、卡班、压车时的补位建议与时效追踪 | MVP 建议做「班次级补位」；车级补位随 L3 |

### 4.2 明确边界（建议）

- **做：** 班前编制、班中预警、人机协同发布与变更告知、基础成功指标沉淀。  
- **慎做 / 后做：** 无完整靠台与车辆数据时的全自动微观指派。  
- **不做（见第十章）：** 装车「排版」、替代考勤合规裁定、默认全分拨开通。

**【待确认】** 首期是「只做人的班次人数与名单」，还是「班次 + 卸/装/移微观指派」一起做。

## 五、建议分阶段范围（MVP / V1.1 / 远期）

以下为**建议分期**，不是排期承诺。

### 5.1 MVP（建议：先打通「预测 → 班次人数/名单 → 发布 → 班次级补位」）

**建议纳入：**

- 选定试点分拨与环节（**【待确认】**名单；禁止默认全开）。
- 提前数日～约一周的货量预测（分拨 / 环节 / 小时；路由粒度【待确认】）。
- 班次编制：各班需要人数、岗位结构、人员建议名单；支持调度确认后发布。
- 正式工 / 外包：至少能在名单与编制中区分展示；编制规则是否分叉【待确认】。
- 异常：请假 / 旷工触发班次级补位建议（不要求首期精确到某辆车）。
- 管理台发布 + 员工侧查看本人班次（App 或现有通道【待确认】）。
- 与现有系统对接：以「读预测与人员主数据、写回班表」为最小集；WMS / 考勤 / 到车系统具体字段与主从【待确认】。

**建议不纳入 MVP：** 卸/装/移到车级微观指派；全自动无确认改班；全网分拨。

### 5.2 V1.1（建议：班中到车协同）

- 接入预计到达 / 靠台 / 卡班等，做「车 → 人/组」建议指派（卸优先还是装优先【待确认】）。
- 忙闲判断与压车预警和补位联动。
- 移动环节精确到卸货口（依赖 DOC3；数据就绪度【待确认】）。

### 5.3 远期（建议：闭环优化）

- 人效、件均重、质量反馈反哺画像与排班引擎。
- 更多用工策略（多技能、跨班支援规则）与分拨个性化策略包。
- 在人机协同稳定后，评估部分场景全自动发布（需单独决策）。

## 七、关键业务流（上班前排班、班中到车指派、请假旷工补位）

### 7.1 上班前排班（MVP 主路径，建议）

1. 系统按预测生成未来 N 日（建议与「提前约一周」对齐，**【待确认】** N）各班人数与岗位结构。  
2. 结合人员技能、出勤、偏好、用工类型生成建议名单。  
3. 调度员在管理台调整并**确认发布**；员工可查本人班次。  
4. 发布后的变更必须告知相关人（见第八章），禁止静默覆盖。

### 7.2 班中到车指派（建议 V1.1+）

1. 到车/预计到达更新后，系统给出卸/装/移任务的人/组建议（是否做微观指派【待确认】）。  
2. 调度确认或按规则半自动生效。  
3. 压车、靠台变更、卡班触发重算建议。

### 7.3 请假、旷工补位（MVP 建议做班次级）

1. 考勤或人工登记触发缺员。  
2. 系统按技能、工时、当前忙闲给出补位候选人。  
3. 调度确认；记录补位时长与是否影响班次人数达标（指标口径【待确认】）。

## 八、人机协同原则（算法建议 + 调度确认；禁止系统擅自改已发布班表而不告知）

**建议原则（写入产品约束，是否采纳【待确认】）：**

1. **默认「算法建议 + 调度确认」**：首期不以全自动发布班表为默认。  
2. **已发布班表变更必须可感知**：系统不得在不告知调度与当事人的情况下改写已发布结果；告知渠道【待确认】。  
3. **人可驳回并沉淀原因**：驳回用于优化引擎与运营复盘，不惩罚现场必要调整。  
4. **紧急现场以调度为准**：算法超时、数据缺失时降级为人工排班，并标记数据缺口。  
5. **分层采纳可配置**：未来可按分拨开放「半自动 / 全自动」，须单独审批，不作为 MVP 默认。

## 九、成功指标建议（人效、压车、补位时长等，标待确认口径）

以下为**建议指标**，基线与目标值均【待确认】。

| 指标 | 建议含义 | 口径【待确认】 |
| --- | --- | --- |
| 班次人数偏差 | 实际出勤人数 vs 建议/发布人数 | 按班次还是按小时 |
| 人效 | 人均处理量或人均吨/票 | 分环节、是否含外包 |
| 预测误差 | 预测货量 vs 实际货量 | MAPE 或分位误差；目标是否参考约 7% |
| 压车时长 / 压车票数 | 到车后等待卸/装的时间与车辆数 | 起止时间戳来源 |
| 补位时长 | 从缺员确认到补位到岗 | 班次级 vs 任务级 |
| 忙闲均衡 | 班内小时人效波动 | 方差还是峰值比 |
| 调度改动率 | 建议名单被人工修改比例 | 过高/过低的解读方式 |
| 发布准时率 | 班表在约定时点前完成发布 | 约定时点 |

## 十、风险与不做清单

### 10.1 主要风险

| 风险 | 说明 | 缓解建议（非已定） |
| --- | --- | --- |
| 范围膨胀 | 微观指派与全分拨同时上，数据和对接拖死 MVP | 强制分期；分拨白名单 |
| 数据不准 | 预测/到车/考勤延迟导致建议不可信 | 显示数据新鲜度；允许降级人工 |
| 组织阻力 | 调度认为算法抢决策 | 人机协同 + 可驳回 + 不静默改班 |
| 用工合规与外包规则 | 正式工/外包工时与岗位限制未理清 | 规则【待确认】前不做自动强约束 |
| 与排版项目混淆 | 装车排版结论误用于排班 | 文档与评审分开 |

### 10.2 建议「不做清单」（讨论稿立场）

- 不做装车「排版」（货物码放）替代或捆绑。  
- 不默认全网分拨、全环节一次开通。  
- 不在无调度确认时全自动改已发布班表。  
- 不以本系统替代考勤法定合规结论。  
- 不在对接范围未定时承诺「与 WMS/考勤/到车全部实时双向同步」。

## 十一、待确认清单（表格：项|选项|建议默认|影响）

| 项 | 选项 | 建议默认（仅建议） | 影响 |
| --- | --- | --- | --- |
| 分拨适用范围 | 单分拨试点 / 多分拨灰度 / 全网 | **单分拨试点**（禁止默认全开） | 数据、运营、风险面 |
| 适用环节 | 卸 / 装 / 移 / 组合 | 试点分拨的主瓶颈环节（需点名） | 预测与岗位模型复杂度 |
| 正式工 / 外包 | 仅展示区分 / 分规则编制 / 暂不区分 | 名单区分 + 规则【并行确认】 | 编制引擎与合规 |
| 微观指派（装/卸/移到人/组/车） | MVP 不做 / V1.1 做 / 与 MVP 并行 | **MVP 不做，先班次人数与名单** | 对接到车/靠台/WMS 深度 |
| 与 WMS 对接 | 不接 / 只读任务货量 / 读写 | 只读货量与任务结构（范围再拆） | 装车货量与结构准确性 |
| 与考勤对接 | 不接 / 只读出勤请假 / 回写班表 | 只读出勤与请假；回写另定 | 补位与发布闭环 |
