# PRD 结构化润色

## 何时使用

- **仅当用户明确要求润色时**使用，例如：「润色」「正式化」「改成书面语」「按豆包那套改」「白话太重」「更有逻辑」
- **不要**在写完维护页 / 报表 / 增量 PRD 后自动执行
- 日常初稿与业务规则句式：一律按 [pm-prd-writing-style](../pm-prd-writing-style/SKILL.md)（含「业务规则书面表达」）；本 skill **不替代**初稿写作

## 与 writing-style 的分工（保留本 skill 的原因）

| | `pm-prd-writing-style` | 本 skill（`pm-prd-polish`） |
|---|---|---|
| 何时 | **每次写 PRD 默认遵守** | **仅用户点名润色时** |
| 管什么 | 模块归类、表格写法、通俗易懂、**业务规则句式**（禁口语缩略、结论先行、【】「」） | 已有正文的**结构重组**：多分支流程分层、指标「定义：」、价值包装、命名备选等 |
| 不做什么 | 不自动做大段改写 | 不改业务规则；不重复发明句式规范（沿用 writing-style） |

**结论：两套都要。** 句式底线已并入 writing-style，写的时候就该写对；polish 只处理「已写成白话/结构乱、需要点名重整」的存量正文，避免删掉后复杂流程润色无处可归。

## 红线（必须遵守）

| 禁止 | 要求 |
|---|---|
| 擅自改业务规则 | **严格沿用**原文业务术语、字段名、数值约束、时间节点、提示文案；不得补充、删减或改口径 |
| 把建议写成已定 | 原文标「待确认」的，润色后仍标「待确认」 |
| 回改无关历史版本 | 多版本串联文档只润色用户指定版本；未点名则只润色最新一版 / 本轮刚写的版本 |
| 大面积连续加粗 | 仅标注核心定义、关键条件、核心字段、核心指标、计算口径等关键词 |
| 绕过句式底线 | 润色后仍须符合 writing-style「业务规则书面表达」 |

润色完成后启用 [pm-review](../pm-review/SKILL.md) 自检：重点查「润色是否带偏规则」。

## 工作流

1. 确认润色范围（文件路径、版本号、整章还是某一节）。
2. 通读目标正文，按下方场景归类（一条内容可同时命中多个场景）。
3. 先按 writing-style 校正句式/术语/【】「」；再按命中场景做结构重组；**先保规则准确，再调结构**。
4. 改完对照原文扫一遍：字段名、限额数字、提示文案、状态枚举是否一字未改错。
5. 进入 `pm-review`；向用户说明：改了哪些结构/语气，业务规则有无变动（应写「无」）。

---

## 通用要求（所有场景）

- 正式、严谨、专业中立；剔除碎片化与冗余。
- 复杂规则按「前置条件 → 判断分支 → 执行动作 → 结果输出」递进；层级列表对齐。
- 核心定义、关键条件、核心字段、核心指标、计算口径可加粗；禁止大段加粗。
- 业务术语、字段名、数值、时间节点与原文一致。

## 分场景执行细则

### 场景 1：单条业务规则规范化改写

输入特征：单句 / 短条口语化的业务判定、匹配、取值规则

执行要求：

- 明确规则的适用主体、前置条件、判定逻辑、执行结果；
- 按 writing-style「业务规则书面表达」改写（结论先行：支持 / 不支持 → 路径）；
- 核心约束条件加粗标注。

### 场景 2：复杂流程类规则结构化梳理

输入特征：多层嵌套、多分支判断的匹配流程、校验逻辑（如方案匹配规则）

执行要求：

- 先提炼所有分支共用的公共校验条件，前置说明，减少重复表述；
- 按优先级从高到低梳理判断层级，每一层级明确「校验内容→命中 / 未命中分支→对应动作」；
- 层级间明确递进关系（如 “匹配失败则进入下一层级校验”）；
- 使用嵌套有序列表呈现，层级对齐统一。

### 场景 3：指标 / 术语定义标准化描述

输入特征：对业务指标、统计口径的口语化说明

执行要求：

- 统一以「定义：」作为开头；
- 明确指标的统计主体、统计范围、计算逻辑、特殊约束；
- 统计维度、限定条件（如 “仅取扫描时间最新的一次”“对应操作类型”）必须加粗明确；
- 表述精准无歧义，避免模糊性描述。

### 场景 4：计算逻辑补全与示例泛化

输入特征：给出计算示例，要求补全对应分支的通用计算规则

执行要求：

- 基于示例数据提炼通用计算逻辑，将具体数值替换为通用业务字段；
- 与已有规则的结构、层级、表述风格保持完全一致，无缝补入对应分支；
- 明确计算公式、取值来源、精度要求（如结果截取 6 位小数）；
- 区分不同身份 / 类型的计算口径，避免逻辑混淆。

> 注意：仅当用户**明确要求**根据示例补全通用规则时使用本场景；默认润色**不得**从示例反推并新增原文没有的规则。

### 场景 5：功能需求与价值包装优化

输入特征：功能痛点、用户调研、需求价值的零散描述，要求优化表述 / 升级命名

执行要求：

- 功能命名：提供多档位备选，至少包含：
  - 基础业务名：直白表述功能用途，适配菜单 / 按钮场景；
  - 专业高端名：贴合数字化运营口径，适配 PRD 正式章节、需求评审场景；
- 需求价值：分点，每点 `**价值标题**：` 加一句业务后果（控成本、少对账、少人工补差、配置可按方案放开）。标题写结果，不写「新增某字段 / 改为某规则」。不要按「业务效率、技术减负、数据质量、运营能力」四个空维度硬套。写法见 [pm-incremental-prd](../pm-incremental-prd/SKILL.md)「需求价值」。
- 痛点描述：结构化提炼核心问题，明确影响范围与业务后果。

> 功能命名多档备选：仅当用户要求「起名 / 改名 / 升级命名」时输出备选清单；纯润色正文时不额外堆命名方案。

### 场景 6：业务进度 / 事项正式化表述

输入特征：口语化的工作进度、事项同步说明

执行要求：

- 明确动作主体、执行对象、数据范围、当前状态四个要素；
- 表述简洁正式，适配工作汇报、需求同步、变更通知场景。

### 场景 7：补充备注类要求规范化

输入特征：零散的开发备注、数据要求、补充说明

执行要求：

- 提炼核心动作、操作对象、设置目的；
- 以「备注：」统一开头，表述清晰正式，适配 PRD 备注栏、补充说明模块。

## 自检清单

- [ ] 业务术语、字段名、数值、提示文案、状态枚举与原文一致？
- [ ] 是否符合 writing-style「业务规则书面表达」（无口语缩略、结论先行、【】「」）？
- [ ] 复杂规则是否已按「前置→分支→动作→结果」或「命中/未命中」分层？
- [ ] 术语/指标是否用「定义：」写清主体、范围、计算、约束？
- [ ] 加粗是否只落在核心词，无大段加粗？
- [ ] 是否未借润色之机补充原文没有的规则？
