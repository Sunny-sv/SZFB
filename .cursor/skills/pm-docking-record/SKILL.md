# 需求对接记录：转写稿转标准文档

## 何时使用

- 用户提供原始会议转写（"说话人 1 00:00"这种格式，常见于飞书妙记/腾讯会议转写导出）
- 用户口述一段对接内容，要求整理成正式的「对接记录」文档
- 用户说「整理对接记录」「按 xxx对接记录 的格式整理」「转写稿弄成对接纪要」

**不替代：** `pm-discuss-challenge` 管"讨论怎么补视角、怎么呈给用户确认"；本 skill 管"已经聊完的转写稿，怎么落成归档用的对接记录文档"。两者可配合：先用本 skill 提炼转写稿结论，再用 `pm-discuss-challenge` 补充遗漏视角。

## 核心原则

| 原则 | 要求 |
|---|---|
| 只提炼转写稿里明确说的 | 不脑补转写稿没提到的规则；含糊/讨论中途反复、最终没敲定的地方写「待确认」，不要选一个自己觉得对的写成结论 |
| 只记最终结论 | 转写稿里常有"一开始想的 A，讨论后改成 B"，正式文档只写**最终结论**；转折过程若关键到影响理解，在备注里提一句即可，不铺陈讨论过程 |
| 明确"不做"的也要记 | 转写稿里说"先不做""没必要""不需要"的功能点要写进结论表或备注，避免以后被当成遗漏重新提出 |
| 口语转书面 | 转写稿是口语（"对对对""我这么说吧""你懂我意思吗"），整理时提炼成简洁书面表达，不照抄语气词和重复口癖 |
| 无关闲聊不进文档 | 转写稿里跟需求无关的寒暄、设备问题（"听不见""信号不好"）等直接忽略 |

## 输出结构

参照 `docs/奖罚/需求对接记录/VIP操作补贴自动录入对接记录.md` 的固定结构：

```markdown
# {需求名}对接记录

> 整理日期：{YYYY-MM-DD}
> 需求负责人：{姓名，不确定则问用户或留空}
> 对应 PRD：{有则填 [xxx.md](相对路径) VX.X.X，没有就删掉这行}

## 对接诉求

1. {业务方要什么、已知约束——2~5 条，来自转写稿}
2. ...

## 已确认结论

| 项 | 结论 |
| --- | --- |
| {规则点1} | {结论} |
| ... | ... |

## 备注

1. {边界情况、例外、"不做"的点、需要留意的风险}
2. ...
```

- 结论表是核心，尽量把转写稿里聊清楚的规则都拆成「项-结论」两列，方便后续核对，也方便直接抄进 PRD
- 若转写稿信息量大、涉及具体取数字段/表现有截图，可仿照 VIP 那篇加一个「xxx取数字段」之类的小节，原样列出讨论中提到的字段
- 遇到转写稿没聊清楚、明显前后矛盾、或需要产品经理拍板的点，不要编结论：单独列「待确认」（可并入备注），照 `pm-discuss-challenge` 的标注习惯写清楚具体没定的是什么

## 产出前自检

- [ ] 结论表里每一条都能在转写稿里找到依据，没有脑补
- [ ] 转写稿里提到"不做"的点写进了备注，没有漏掉
- [ ] 含糊/中途反复未有最终结论的地方标了待确认，没有替业务拍板
- [ ] 口语已改写成书面表达，无关闲聊已去掉
- [ ] 落盘路径和文件名已与用户确认

## 落盘位置

默认放在需求所属项目目录下，若该项目已有类似 `需求对接记录/` 子目录（参考 `docs/奖罚/需求对接记录/`）则跟随放进去，文件名格式「{需求名}对接记录.md」。写入前提醒用户：不覆盖已有同名文档（红线规则）。
