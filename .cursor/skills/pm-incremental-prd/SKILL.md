# 版本增量 PRD 写作规范

## 何时使用

- 写 **V1.1.0 / V2.0.1** 等相对上一版的增量 PRD
- 用户说「只写改了什么」「看不懂，重写」「不要引用前面章节」
- 计算逻辑、匹配规则、配置改版等**规则类**增量文档
- 已有 V1.0.0 / V2.0.0 基线，本版只交付变更部分

**不替代** pc-maintain-prd / pc-report-prd：新建维护页、报表页仍用对应 skill 的全量结构；本 skill 管**版本增量**写法。

## 首版未上线：是否新开版本（必问）

功能**尚未上线**、PRD 里只有 **`### V1.0.0`（或同文件首版章节）**、没有已交付现网基线时：

| 默认 | 须先问用户 |
|---|---|
| **直接改首版章节**（合并进 `### V1.0.0`），概述/背景表仍只保留一行 V1.0.0 | **禁止**自行追加 V1.1.0 / V2.0.0 等「增量版」 |

**问法（写 PRD 前）：**「这个功能还没上线，改动是继续写在 V1.0.0 里，还是新开 V1.1.0？」

| 用户答复 | 怎么写 |
|---|---|
| 继续写 V1.0.0 / 还没上线 / 不要新版本 | 改 `### V1.0.0` 正文与概述一行；**不**新增版本行、**不**新建 `### V1.1.0` |
| 新开 V1.1.0（或指定版本号） | 按下方「多版本串联」：历史节不动，追加本版行 + 新建版本章节 |

> **例外说明：** 「禁止回改历史版本正文」针对**已上线、已交付**的历史版本。首版未上线时，V1.0.0 仍是草稿首版，**允许且默认**直接修订 V1.0.0，不算违反「不改历史版本」。

## 写法风格

必须同时遵守 [pm-prd-writing-style](../pm-prd-writing-style/SKILL.md)：只写有用内容；结论先行少解释；维护页/报表页的字段改动**必须按查询条件、按钮操作、数据列表分区写（强制，无用户明确要求也要遵守）**，禁止一整段跨区域编号清单；表格长内容拆有序列表（嵌套用缩进），展示规则等非字段内容放表格最后说明行；同版内重复规则可「按上述「字段名」」引用；语言用日常产品经理口吻。详见 writing-style「描述密度与引用」。

用户明确要求正式书面语润色时，再启用 [pm-prd-polish](../pm-prd-polish/SKILL.md)；润色不得改业务规则。平时写完不要自动润色。

## 核心原则

| 原则 | 要求 |
|---|---|
| **只写改动** | 正文只描述本版相对上一版的新增、删除、调整；未改内容不单独成节、不展开 |
| **每版必写背景节** | **要解决的问题、用户调研、产品方案、需求价值**（或多版本串联文档里对应章节）**每个新增版本都要补一行/一段**；写清业务背景与为何改。用户调研与产品方案同属「业务分析」，**两项都要写** |
| **不知背景先问** | 写背景节前若不清楚「现在哪里错了、业务真实场景、为何要改」，**主动问用户 2～4 个关键问题**，禁止编造公司内部原因或 silent 默认 |
| **缺信息先问、禁止瞎猜** | 用户原话：如果你发现我给你的信息不完整，或者你做方案写文档这些需要其他我没给的信息要告诉我，我给你补充，不要靠你自己猜。触发时机、现网落池、取数字段等写不清时先向用户要材料，禁止猜完写进 PRD（见 `pm-ask-before-guess`） |
| **不写版本概述** | **禁止**写「本版改动概述」「版本概述」「改动范围编号列表」这类总述小节；改了什么直接落在规则正文（查询条件 / 按钮 / 数据列表 / 判定步骤等）里写清 |
| **不改历史版本正文** | 同一份多版本串联 PRD 里，**已上线/已交付**的历史版本章节**禁止回改原文**；本版规则写在**新建版本章节** + 概述表追加一行。**首版未上线**见上文「首版未上线：是否新开版本」— 默认改 V1.0.0，开新版本须先问用户 |
| **禁止序号互引** | 不写「见 4.3」「进入 4.5～4.6」「按 5.2 取值表」「与 V2.0.0 一致（见第四章）」。**同版内**相同规则可写「按上述「字段名」xxx 规则」（见 writing-style）；跨历史版本 / 章节序号互引仍禁止 |
| **禁止符号化** | 不用 D、v(d)、∀、∈ 等数学写法；区间写「下限 ≤ 实际值 < 上限」 |
| **业务可读** | 读者是研发、测试、运营；用日常业务说法 |
| **自洽可审** | 单读**本版章节 + 本版背景节**能评审本版交付；本版改动写清；未改内容写「沿用现网，本版不改」即可，不抄历史整表 |
| **不重复维护侧内容** | 维护页已写清的字段枚举、页面限制、导入规则，不在计算逻辑里重复 |

### 背景节写什么（每版必填）

| 节 | 写什么 | 不要写成 |
|---|---|---|
| **要解决的问题** | 现状怎么干、卡在哪、会出什么业务后果（可点名页面/字段/口径冲突） | 空话「效率低」「体验差」；纯框架小标题堆砌 |
| **用户调研** | 业务已确认的诉求、一期范围、边界口径；与问题呼应 | 把字段清单、匹配步骤写进调研；「谁在用」模板腔 |
| **产品方案** | 本版具体做什么、改名什么、沿用什么；短句分条 | 研发实现细节、表结构；空泛「首句定调」无实质 |
| **需求价值** | 每条「**结果型标题**：业务后果」；须对得上前面的问题 | 复述产品方案字段；空话「降本增效」「提升体验」 |

**背景不足时先问再写**，例如：

1. 现在错在哪一步、谁会碰到？
2. 有没有具体例子（日期、岗位、单据）？
3. 期望改成什么数据源 / 规则？
4. 命中后怎么处理（算老员工 / 不区分新老等）？

### 背景四节写法（正式、可上 PPT；强制）

面向业务评审与汇报：语气**书面、正式**，内容**具体、有后果**；可直接摘进 PPT。规则正文（「五、详细需求」/ `### Vx.y.z`）仍按 writing-style 压缩。

**总原则：**

| 要 | 不要 |
|---|---|
| 写清「现在怎么做 → 卡点 → 业务风险/成本」 | 只写「能力缺失」「体验不好」 |
| 书面语（须、尚无、命中、计发、口径、贯通） | 口语堆成全文；也不要照抄他稿原文 |
| 问题与价值一一对应 | 价值写方案清单；问题写价值口号 |
| 范围/边界写进调研或方案一句即可 | 用「改动前后」大表复述规则正文 |

**要解决的问题（分条，勿挤成一段）：**

| 推荐 | 反例 |
|---|---|
| 先写现状能力（已能筛出 / 已有某 Tab），再写缺口（尚无单价维护 / 薪资未挂字段） | 「系统不支持独立计算，效率低、易出错」 |
| 点明口径冲突后果（挂不上方案、重复计发、对账补录） | 只写「名称易混淆」不写会怎样 |
| 需要时点出命名/入口混淆带来的误选 | 用 `1. **能力补齐。**` 这类空框架小标题撑场 |

**用户调研：**

| 推荐 | 反例 |
|---|---|
| 已确认的诉求、一期范围、命名/支援/外包等口径，短句分条 | 「谁在用：A；核心诉求：B」六段模板 |
| 不在本需求的动作一句注明去向 | 把新增 Tab 字段、匹配步骤写成调研 |

**产品方案：**

| 推荐 | 反例 |
|---|---|
| 直接写：新增/更名/同步什么；计价维度、环节范围；流程沿用哪套 | 「在现有能力上拆出两套…」长铺垫后再列清单 |
| 「业务规则不变 / 本版不另建审批」点明不动边界 | 为背景单独再做一张「改动前后」对照表（细则放规则节） |

**需求价值：**

| 推荐 | 反例 |
|---|---|
| `1. **核算线上化**：…` / `2. **口径隔离、规避重复计发**：…` — 标题是结果，正文是谁少挨什么事 | `1. **算得清：**` 过口号；或把「新增某某字段」当价值 |
| 与问题条对齐（线下乘价 → 线上化；双口径叠加 → 隔离计发） | 「提升效率、降低成本、规范流程」万能四件套 |

句式对照（正例以薪资线上化操作大票类为准）：

- 问题正例：`操作大票货量已可在【操作货量查询】按操作类型单独识别，但系统尚无对应单价维护能力。分拨仍需按月导出明细、人工拆分至人员后再套用线下单价，核算周期长、差错难定位、结果难追溯。`
- 价值正例：`1. **核算线上化**：操作大票单价纳入系统维护后，可替代分拨按月导表明细、人工拆分、线下乘价的作业方式，缩短核算周期，提升差错可追溯性。`
- 反例：`1. **补齐独立计价能力：** 支撑单独算薪，减少人工补差。`（空、不具体）

**标杆：** [`docs/薪资线上化/基础提成方案维护.md`](../../docs/薪资线上化/基础提成方案维护.md) **V8.0.0** 二～四节（问题 / 调研 / 方案 / 价值）。展示类亦可参考 [`docs/百分比重量/PDA操作结算重量展示.md`](../../docs/百分比重量/PDA操作结算重量展示.md)，但增量薪资/维护类默认向基础提成 V8.0.0 对齐。

### 多版本串联文档怎么改

适用于 `docs/薪资线上化/*.md` 这类「一份文件里按 V1.0.0 / V2.0.0 … 往下堆」的 PRD。

| 做 | 不做 |
|---|---|
| 概述版本表**追加**本版一行 | 回改 `### V1.x` / `### V2.x` 等历史节原文 |
| 「要解决的问题 / 用户调研 / 产品方案 / 需求价值」各**追加本版一行**（用户调研与产品方案同属业务分析，两项都要有） | 跳过背景节、或只写规则不写背景；只写产品方案不写用户调研 |
| 在「需求描述」下**新增** `### Vx.y.z`，按增量类型写规则正文（三区 / 匹配逻辑表等）；**新建文档首版先写 `### V1.0.0`** | 写「本版改动概述」总述小节；或用 `### 5.2.1` 代替版本号；报表仅匹配却空造三区 |
| 本版改动写清：删什么、改成什么、命中后怎么处理；同版重复规则可按上述引用 | 只改历史节、不写本版章节；或「与 V2.0.0 一致，略」 |
| 维护页多 Tab 共用复杂规则：先 `#### 公共规则` 再各 Tab 三区 | 每个 Tab 按钮列复制四遍重叠算法；或「本页做两件事」复述三区 |

> **反例**：改复职判定时回改 V1.3.0 / V2.0.0，再写一节「本版改动概述」→ **错误**。  
> **正例**：历史节不动；问题 / 用户调研 / 产品方案 / 价值各加本版行；新建 `### V8.2.1` 直接写判定步骤。

## 禁止写法 vs 推荐写法

| 禁止 | 推荐 |
|---|---|
| 本版改动概述 / 版本概述（1. 2. 3.） | 直接写「区分新老员工逻辑」「查询条件」等模块规则 |
| 不知背景就编造问题原因 | 先问用户再写背景节 |
| 见 4.3 方案层级 / 与 V2.0.0 一致（见第四章） | 本版需要的步骤写在本版；同版内可「按上述「字段名」」 |
| 与 V2.0.0 一致，略 | 不写；没列出的内容默认未改；若整块未改写「沿用现网，本版不改」 |
| `[800, 99999.99)` | 800～99999.99（正文说明前闭后开即可） |

## 推荐文档结构

多版本串联在同一文件时（薪资线上化等）：

```
一、概述 → 版本表追加本版一行
二、要解决的问题 → 追加本版一行（必写，有场景）
三、业务分析
    3.1 用户调研 → 追加本版（必写；无则写「无」及原因）
    3.2 产品方案 → 追加本版一行（必写）
四、需求价值 → 追加本版一行（必写）
五、详细需求 → 新增 ### Vx.y.z
    （无「本版改动概述」）
    按类型写：公共规则（若需）+ 三区 / 或匹配逻辑表 / 或判定步骤 …
    **适用范围**：已有功能迭代时，须先按规则 `pm-org-scope` 问用户「本版 PRD 要不要写适用范围」；说要写才写，说不用写则本版不写该节。新功能首版默认写。禁止每个增量版默认都挂适用范围。
```

独立增量文档（如单独 V2.0.1 文件）同理：先写问题、用户调研、方案、价值，再写规则正文；**不写**「本版改动概述」专节。

**不写**「V1.0.0 全文」「本版没改什么」等基线复述。

## 规则类章节写法

删除、新增、调整放回所属模块，不单独堆「删除项」总表。

用 **步骤 + 结果表 + 业务示例**，不用伪代码符号。

判定步骤以流程图或步骤表**二选一为主载体**即可；二者并用时，**表/图之后禁止复述**已写清的分支与枚举，只写尚未出现的增量信息（如取值来源一句）。节名、修订说明、跨文档引用锚点遵守 [pm-prd-writing-style](../pm-prd-writing-style/SKILL.md)「通俗易懂」：禁用「落数」「固化」「分桶」等当标题，改用「写入货量明细的字段」类业务说法。详见 writing-style「同节不复述」。

### 按增量类型选正文结构（强制）

| 增量类型 | 正文怎么写 |
|---|---|
| **维护页字段 / 按钮 / 列表** | 可选 `#### 公共规则`（多 Tab 共用复杂规则时）→ 各 Tab **查询条件 → 按钮操作 → 数据列表**；见 [pc-maintain-prd](../pc-maintain-prd/SKILL.md) |
| **纯计算 / 匹配逻辑**（无维护页界面改动） | `#### 匹配逻辑`（或判定步骤）用表写清增量项 + 可选业务示例 + **验收要点表**；**不套**查询/按钮/列表三区 |
| **报表只改匹配 / 取数 / 闸门**，页面查询条件与列表字段本版未改 | 同「纯计算 / 匹配逻辑」；**不要**为空造查询/按钮/列表 |
| **报表改了查询 / 按钮 / 列表字段** | 仍按 [pc-report-prd](../pc-report-prd/SKILL.md) 三区写有改动的区域 |

匹配逻辑表推荐列：`项 | 说明`（需要时加 `tab` 或适用范围列）。项如：触发前置条件、新增/调整字段匹配规则、匹配条件数量、是否进入下一套规则（闸门）。

```markdown
### V2.3.0
#### 匹配逻辑
|项|说明|tab|
|---|---|---|
|匹配条件数量|本版新增非空字段各计 1；是否叠加特殊单价不计入|实时特殊、流水线特殊|
|新增字段匹配规则|操作人：取扫描人，集合有交集即命中；…|同上|
|是否叠加特殊单价|命中货量方案且=否 → 不进特殊单价；=是或未命中货量 → 可进|全部|

#### 验收要点
|序号|验收要点|
|---|---|
|1|…|
```

**跨文档：** 维护页已写的枚举/导入/页面限制，计算与报表增量**不重复**；对齐对侧写「与【某某维护】一致」即可。配置开关在维护页，运行时闸门写在本计算/报表节；细则见 writing-style「跨文档取舍」。

### 验收要点

只验收**本版变更**；回归项可保留 1 条「与改版前一致」。

**强制用表格**列出（与 [pm-prd-writing-style](../pm-prd-writing-style/SKILL.md)「验收要点」一致），禁止纯编号列表：

|序号|验收要点|
|---|---|
|1|……|

## 写作前检查

- [ ] **首版未上线时：是否已问用户「改 V1.0.0 还是新开版本」？** 未确认前是否避免自行追加 V1.1.0？
- [ ] 是否只写本版增量，未把基线 PRD 又抄一遍？
- [ ] **要解决的问题、用户调研、产品方案、需求价值是否都有本版内容？** 背景是否来自用户确认（未确认是否已先问）？是否按「背景四节写法（正式、可上 PPT）」：具体场景+后果、书面语、价值对得上问题（标杆：基础提成方案维护 V8.0.0）？
- [ ] **是否未写「本版改动概述 / 版本概述」？**

## 交付前必审

写完增量/规则 PRD 后，**先启用** [pm-review](../pm-review/SKILL.md) 做逻辑/结构/写法审查，输出「待你确认」清单后再结束本轮（用户明确说「先别审」除外）。默认只提问题，不擅自改文档。
