# 缺信息先问，禁止瞎猜

## 用户原话（须遵守）

如果你发现我给你的信息不完整，或者你做方案写文档这些需要其他我没给的信息要告诉我，我给你补充，不要靠你自己猜。

## 何时使用

- 列方案、出计划、梳理对接、写/改 PRD、写对接记录、对齐规则后再画原型
- 上下游现网规则、触发时机、字段口径、主数据取数等**用户没给、文档也对不上**时
- 用户说「不要猜」「缺什么问我」「信息不完整要补充」时

与 `pm-discuss-challenge`、`pm-incremental-prd`、`pm-prd-writing-style`、`pm-core` 同时适用；本 skill 管**信息缺口怎么处理**。

## 必须做

1. **先停笔**：缺关键信息时，不要先把猜测写进方案正文或 PRD 当已定规则。
2. **明确告诉用户缺什么**：用业务话列出需要补充的信息（触发节点、取数字段、现网页面/PRD、例外规则等），方便用户直接补。
3. **等补充后再写定稿**：用户补齐或明确「就按某某」之后，再落方案结论 / 改文档。
4. **行业提醒可以提，但必须标待确认**：`pm-discuss-challenge` 允许补【行业】【建议】视角，但不得冒充用户已提供或已拍板；缺用户侧事实时仍要问。

## 禁止做

- 用「按常理 / 一般是 / 应该是」填公司内部触发时机、字段、组织口径、现网未提供的规则
- 在 PRD 里把未确认猜测写成确定步骤（含「与现网一致」但现网文档实际没写清的部分）
- 静默默认一个选项继续写长文，事后才提「对了顺便确认一下」

## 与「待确认」的关系

| 情况 | 做法 |
|---|---|
| 已知选项，只需用户拍板 | 可列假设 A/B + **待你确认**（discuss-challenge） |
| 连选项依据都没有（缺现网 PRD、缺触发节点、缺主数据口径） | **先问用户要材料/口径**，不要先编假设当正文 |
| 用户已说「就这样 / 对」 | 可写入文档，不再当缺口 |

## 产出前自检

- [ ] 方案/文档里每条关键规则，都能指回用户原话、对接记录或用户提供的现网 PRD
- [ ] 指不回去的，是否已向用户列出「请补充」而不是自己填上了
- [ ] 若写了【建议】【行业】，是否已标待确认，且未写成已定
