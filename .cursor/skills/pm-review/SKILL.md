# PRD / 原型审查

## 何时使用

- **交付前必审**：刚用 `pc-maintain-prd` / `pc-report-prd` / `pm-incremental-prd` / `pc-prototype` 写完时，**先跑本审查**（除非用户明确说「先别审」）。若本轮刚做过 [pm-prd-polish](../pm-prd-polish/SKILL.md)，审查重点查规则是否被润色带偏。
- 用户说「审查 PRD / 检查原型 / 挑挑刺 / 写完帮我过一遍 / PRD 自检 / 自己检查 / 有问题直接改」
- 评审前想确认：逻辑有没有打架、结构合不合标准、原型展示/交互有没有问题

**不替代：** 写作用对应 PRD/原型 skill；讨论补方案用 `pm-discuss-challenge`；正式润色仅在用户点名时用 `pm-prd-polish`。本 skill 管**审已有产出物**，并按下方规则决定改不改文件。

## 红线

| 禁止 | 要求 |
|------|------|
| 拿不准还瞎改 | 缺业务拍板、跨文档未决策、与用户已定结论可能冲突时，**只问不改** |
| 改了不说明 | 凡改文件，回复里必须列「已改项」；不得假装没动过 |
| 编造冲突 | 不拿未确认的公司内部规则当「冲突」依据 |
| 装成事实 | 拿不准标「待你确认」，严重度用「提醒」；不把猜测写进 PRD 当已定规则（与 `pm-ask-before-guess` 一致） |
| 用户只要清单时硬改 | 用户明确说「先别改 / 只出问题清单 / 先别审改」→ **只输出清单，不改文件** |

## 改与问（默认）

审查默认：**能改的直接改，不能定的只问。**

| 类型 | 做法 |
|------|------|
| **直接改** | 写法（`<br>`、全称、命名混乱）、文档内自洽（漏写触发窗、取不到怎么办、重复装单）、与**本对话/本仓库已确认**口径一致的补全、结构明显缺块且补法唯一 |
| **只问不改** | 要业务拍板（是否上提前发车、二次移动是否拦建单等）、与另一份已定版 PRD 冲突且用户未说以谁为准、多种合理解且会改变业务结果 |
| **只出清单不改** | 用户点名「只审查 / 先别改」 |

用户说「自己检查 / 有问题直接改 / 改掉能改的」→ 按上表执行，**不要**再默认整表只列问题等确认。

## 工作流（固定顺序）

1. **确定审查对象**
   - 用户指定了路径 → 用该文件
   - 本轮刚写出的 PRD/原型 → 用刚产出的文件
   - 未指定且上下文没有 → 先问路径（PRD / 原型 / 两者对照）
2. **读目标文件**（PRD Markdown 和/或 `docs/**/*.html` 业务原型）
3. **按类型读标准**（只读需要的，见下表）；详细检查项读 [checklist.md](checklist.md)
4. **过一遍 checklist**，只记真实问题，不凑条数
5. **分流处理**
   - 属「直接改」→ 改文件
   - 属「只问不改」→ 记入待确认清单
6. **按下方模板输出**（含已改项 / 待确认）；无问题写「未发现冲突 / 结构与标准一致」

### 按类型对照哪些标准

| 审什么 | 必须对照 |
|--------|----------|
| 维护页 PRD | [pc-maintain-prd](../pc-maintain-prd/SKILL.md) + [pm-prd-writing-style](../pm-prd-writing-style/SKILL.md) + [pm-component-catalog](../pm-component-catalog/SKILL.md) |
| 报表 PRD | [pc-report-prd](../pc-report-prd/SKILL.md) + writing-style + component-catalog |
| 增量/规则 PRD | [pm-incremental-prd](../pm-incremental-prd/SKILL.md) + writing-style |
| 正式润色后的 PRD | [pm-prd-polish](../pm-prd-polish/SKILL.md)（重点查润色是否带偏规则） + writing-style |
| HTML 原型 | [pc-prototype](../pc-prototype/SKILL.md) + 母版 `docs/_共用/PC端通用框架.html` |
| 两边都有 | 上表对应项 + checklist「原型 ↔ PRD」对齐 |

分不清文档类型时：看章节（有「查询条件/按钮操作/数据列表」多为维护或报表；只写本版改动多为增量；`.html` 在 `docs/{项目名}/` 为原型）。

## 输出模板

```markdown
## 审查结论
一句话：已改 N 项；另有 M 项待你确认（含 X 阻断）/ 通过无可改项

## 已改项
| 编号 | 位置 | 改了什么 |
|------|------|----------|
| 1 | … | … |

（无改动则写「无」）

## 待你确认（无法自定）
| 编号 | 严重度 | 类型 | 位置 | 问题 | 需要你拍板 |
|------|--------|------|------|------|------------|
| 1 | 阻断 / 建议 / 提醒 | 逻辑冲突 / 结构 / 写法 / … | … | … | 选项 A / B 或一句话问法 |

（无则写「无」）

## 已通过项（简略）
- [ ] 仅列关键通过项
```

用户明确只要清单、先别改时：仍用原「问题清单」表，**不要**「已改项」节，且不改文件。

### 严重度

| 级别 | 何时用 | 对用户的含义 |
|------|--------|--------------|
| **阻断** | 逻辑互相打架、缺必填结构模块、原型顶栏/侧栏/四模块骨架被改坏 | 建议先处理再拿去评审 |
| **建议** | 写法不合规范、交互演示缺失、易误解 | 能改则已改；不能定则列入待确认 |
| **提醒** | 行业常见坑、口径需业务拍板、可能冲突但证据不足 | 不能定则只问 |

### 类型取值（表内只用下列之一）

`逻辑冲突` · `结构` · `写法` · `原型布局` · `交互` · `原型-PRD不一致`

## 写法约定

- 结论先行；待确认项要能直接回答「改成… / 选 A / 选 B」
- 正文中文；位置写清章节名或原型模块（筛选区/按钮区/列表列名等）
- 已改项写清改前问题与改后口径，不要只写「已优化」
- 一次审查优先处理真正影响评审的项；同一根因合并

| 阶段 | skill |
|------|--------|
