# PRD / 原型审查检查项

审的时候按审查对象勾选对应节；不必全文复述标准 skill，有疑点再打开对应 SKILL。

---

## 一、PRD 逻辑

- [ ] 同一字段/规则前后是否矛盾（默认值、空值是否过滤、匹配条件、未命中怎么办）
- [ ] 同一枚举/状态在不同章节写法是否一致
- [ ] 维护页已禁止维护的项，计算/报表是否仍假设可以配、可以命中
- [ ] 导入拒收规则与列表可展示/可编辑是否打架
- [ ] 维护页有导入时：是否按「上传触发 → 导入校验（对齐新增）→ 唯一性（按维度拆开 + 有效期限交集）→ 整份成败 + 失败文件」写全，而非「支持导入 / 整份失败」一句带过
- [ ] 权限说明与按钮/数据可见范围是否矛盾
- [ ] 增量文档是否出现「见 X.X / 第 X 章」「与 Vx 一致（见上文）」等**章节序号互引**（违规）；同版内复杂规则「按上述「字段名」xxx 规则」允许；简单查询条件应写全、不宜「按上述」
- [ ] 跨表取数是否写清：匹配条件 → 取哪个字段 → 未匹配怎么办；两边口径是否同一套
- [ ] 生效/失效、跨月切点、覆盖规则等时效逻辑是否自洽（若有）

---

## 二、PRD 结构

### 维护页（对照 pc-maintain-prd）

- [ ] 是否有：概述（版本修订表）→ 要解决的问题 → 业务分析（含 3.1 用户调研、3.2 产品方案，两项都要写）→ 详细需求
- [ ] 详细需求是否含：相关链接、权限、全局注意事项
- [ ] 各 Tab/模块是否按 **查询条件 → 按钮操作 → 数据列表**（有变更记录则单独一节）
- [ ] **字段增量是否按三区落表**，而非「#### 某某字段」下挂一整段跨查询/按钮/列表/导入的编号清单（强制；用户未豁免时违规即记）
- [ ] **多 Tab 共用复杂规则：** 是否用 `#### 公共规则` 写一次（重叠提醒/改名清单等），三区「按上述」引用？**违规：**「本页做两件事」或把查询/弹框/列表细则提前抄一遍；或同一重叠算法在每个 Tab 复制多遍
- [ ] 维护页是否把新增/编辑弹框写进按钮说明列，而不是单独「新增弹框」「编辑弹框」小节
- [ ] 版本表：修订人、日期格式、修订说明是否按规范；版本号与产品方案表是否一致；用户调研是否有本版内容（无则须写明「无」及原因）

### 报表（对照 pc-report-prd）

- [ ] 章节 1～4 是否与维护页总结构一致（版本表等）
- [ ] 各 Tab：查询、导出、列表、定时任务/汇总下钻/终版导入等应有模块是否齐全（无则应写「无」或说明不适用）
- [ ] 明细/汇总/终版差异是否用继承写法，避免大段复制又改漏
- [ ] **本版若只改匹配/闸门、页面字段未改：** 是否用匹配逻辑表（对照 pm-incremental-prd），**未**为空造查询/按钮/列表？若改了页面字段是否仍按三区？

### 增量（对照 pm-incremental-prd）

- [ ] 是否只写本版改动，未整份复制基线
- [ ] **要解决的问题、用户调研、产品方案、需求价值**是否都有本版内容，且问题有具体业务场景（非空话）；用户调研与产品方案是否齐全（无调研须写明「无」及原因）；需求价值是否写成业务帮助（控成本、少对账等），而不是把产品方案（补字段、改规则）再列一遍
- [ ] 背景四节是否**分条可读**（问题/调研/价值宜 `1. **小标题**` + 举例；方案是否说清只改什么、什么零改动；展示/口径类是否考虑「改动前后」小表），而非各节仅一段话
- [ ] 是否出现「本版改动概述 / 版本概述」总述小节（应删除，规则直接写在模块里）
- [ ] 多版本串联文档：是否**未回改**历史 `### Vx.y.z` 章节原文；本版规则是否只出现在新建版本节 + 概述版本表
- [ ] 改动是否按模块归类（查询/按钮/列表/规则主题），而非单独堆「删除项」总表；**维护/报表字段改动是否拆到三区，无跨区域一整段编号清单**
- [ ] **增量类型与结构是否匹配：** 纯计算/匹配 → 匹配逻辑表；维护字段 → 公共规则（若需）+ 三区；报表仅匹配 → 不造空三区
- [ ] 单读本文是否能审本版范围（禁止靠「与上一版一致，略」糊弄）

## 三、PRD 写法（对照 pm-prd-writing-style）

- [ ] 是否只写有用改动；没改的内容没有展开
- [ ] **PC 维护/报表：是否严格按查询条件 / 按钮操作 / 数据列表分区写**（禁止一整段编号清单揉查询+弹框+列表+导入；用户未明确豁免时必检）
- [ ] **公共规则是否用对：** 多 Tab 共用复杂规则用 `#### 公共规则` 合法；把三区细则塞进开篇复述 → 违规；字段改名是否公共列清单、三区只写「原××改名」
- [ ] **Tab/字段主题段首是否过长且与后文三区重复**（选库规则、跟库字段表、可维护字段表、联动长文应下沉到按钮/列表；段首仅 1～2 句职责）
- [ ] **维护页是否写了消费方用法**（命中放行、面单展示、拦截等应只在消费方 PRD；维护页只写字段/校验/展示）；闸门是否外置为「细则见【文档全称】」
- [ ] **两套配置重叠/互斥：** 两边是否各写本侧视角？对齐对侧是否整段抄了矩阵（应「与【某某】一致」）？
- [ ] **验收要点是否用表格列出**（`序号 | 验收要点`，非纯编号列表）
- [ ] 表格长内容是否拆成有序列表（嵌套用缩进）；展示/排序等非字段规则是否在表格最后说明行
- [ ] 原型已确认时，是否复述了页面骨架、模块顺序、有无 Tab 等（应避免）
- [ ] 是否出现 AI 腔：「替代为」「同步更新配置项」「配置内容升级」、改版对比长文、职责旁白等
- [ ] 业务规则是否出现口语缩略（靠/审/补等）、多重否定歧义（如「不靠审不通过自动补」）；是否「支持/不支持」结论先行；模块【】、操作「」是否统一；**页面/菜单是否写全称**（禁止「作业统计」「维护」「报表」「交接单」「薪资」等丢业务名简称；禁止「交接单改名」「薪资新增」；应写【交接单人员提成】改名、【转运人员薪资】新增等）
- [ ] 是否出现研发向用语：存量、刷数、映射、OR/AND、落数、进数（非正式字段名）等（应换成业务说法）；数量比较可用 ≥、≤、<、>
- [ ] 按钮操作是否未默认写查询/重置（无特殊逻辑时）？
- [ ] 字段计算是否写进说明列；复杂重复规则是否一处写全、他处「按上述」；简单查询条件是否各处写全；有无「见下文 / 见第 x 章」
- [ ] 是否结论过长可压成一句却拆成多条解释；复杂分支是否该用流程图却堆逐步文；导出长列是否该外挂却塞进 PRD
- [ ] **规则类章节：流程图/步骤表之后是否复述已写清的分支**（「按上面…」「分两种…」总结腔 → 违规；表后只留尚未出现的增量信息）
- [ ] **节名、修订说明、跨文档引用是否含「落数」「固化」「分桶」等难懂黑话**（应改为写入/记入类业务说法，如「写入货量明细的字段」）
- [ ] 控件是否点名组件目录标准名，是否只写本页业务差异（对照 pm-component-catalog）

## 四、原型展示（对照 pc-prototype + 母版）

- [ ] 是否从 `docs/_共用/PC端通用框架.html` 复制而来（非从零发明布局）
- [ ] **全局结构**完整：顶栏（品牌区 + 蓝底标签栏）+ 侧边栏 + 主内容区
- [ ] **四模块**顺序：筛选条件 → 内容 Tab → 操作按钮 → 数据列表（含分页）
- [ ] 分页是否贴在内容卡片底部**右下角**（`justify-content: flex-end`）；是否为 `.table-area` 直接子元素、**未**放进 `.table-scroll`（数据少时也不紧贴表体悬在半屏、不跟着表滚）
- [ ] 筛选：名称左 + 控件右；默认一行 3 组件；重置/查询在最后一行右侧且底对齐
- [ ] 弹框/表单：字段名与控件左右排列（禁止名称在上、控件在下）
- [ ] 表格：首列复选框；表头与单元格默认居中；**表头字段名单行不换行**（列多时横向滚动，不挤成多行）
- [ ] 单文件 HTML，无 CDN、无后端、无真实 API
- [ ] 页面无「原型说明」黄条、演示备注、临时演示按钮；看起来就是实际业务页
- [ ] 未确认字段是否用通用占位，而未乱编业务名/规则
- [ ] 色值与母版大体一致（顶栏蓝 `#0659d9`、主色、侧栏、内容底、卡片、边框）

## 五、原型交互

- [ ] 母版演示交互是否还在：顶栏汉堡折叠侧栏（`#layout.sidebar-collapsed`）、顶栏/内容 Tab 切换 active、表头全选联动行 checkbox
- [ ] 是否误做了查询、重置结果、分页跳转、菜单路由、表单校验等（线框阶段应克制）
- [ ] 若有多 Tab：切换后列表/按钮差异是否看得见、说得清
- [ ] 若有弹层/抽屉：打开与关闭路径是否完整（演示级即可）
- [ ] 关键操作路径是否断（按钮在但无对应演示态，且 PRD 已依赖该路径时标提醒）

## 六、原型 ↔ PRD 对齐（两边都有时必做）

**逐条对照查询条件表**（不要只扫字段名）：对 PRD 里每一个查询条件，打开原型核对照片级细节。

- [ ] **字段名**是否一致（含全称，如「操作类型」勿写成「类型」）
- [ ] **控件类型**是否一致——**必查单选 vs 多选**（PRD 写「多选下拉框」而原型是普通 `<select>` 单选 → 记问题）；另查：数据权限/人员组件（可多选）是否被画成单行输入却无任何多选示意、区间选择器是否只有单边等
- [ ] **默认值**是否一致（PRD「空、不参与过滤」而原型预填/默认选中某枚举 → 记问题；演示数据须与正式默认区分清楚）
- [ ] 操作按钮名称、是否存在是否一致
- [ ] 列表列名、Tab 名是否一致
- [ ] PRD 有、原型无 → 列出；原型有、PRD 无 → 列出
- [ ] 权限/菜单路径与原型侧栏菜单文案是否明显冲突（有则标）

> 教训：逻辑审查通过不代表控件对齐；「操作类型」一类字段曾出现 PRD 多选、原型单选漏报，审查时必须点名写出。

## 七、产出提醒

- 只把**未通过或存疑**的项写入审查表；通过项可在「已通过项」简略打勾
- 一条问题写清：位置 + 现象 + 建议改法
- 逻辑拿不准时用严重度「提醒」，不要升成「阻断」吓唬人
